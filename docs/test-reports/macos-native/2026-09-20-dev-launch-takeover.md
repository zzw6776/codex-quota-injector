# macOS 开发版接管来源误判修复

- 源码版本：0.1.294；Widget 178、Relay 91。
- 环境：macOS arm64、Node v26.7.0。
- 范围：开发启动入口来源标记、Codex 内部启动保护和隔离启动控制台；测试命令零模型请求、零接管、零重启，不替代正式包启停验收。

## 失效机制与修复

实际正式版 0.1.293 / Widget 176 正在运行。用户明确打开 `启动开发版.command` 后，Terminal 仍继承了 `CODEX_APP_TOOLS_PIPE_PATH`；旧逻辑只检查这个变量，在读取现有实例并进入单实例接管前就把本次启动误判为 Codex 任务内部启动，因此开发版返回成功但没有替换正式注入器。

命名的 `.command` 入口现在写入精确的 `CODEX_QUOTA_DEV_EXTERNAL_START=1`，表示用户明确发起外部启动。来源判定只在工具管道存在且没有该标记时拒绝接管；因此直接从 Codex 任务内部运行 `npm run launch` 仍受保护，而 `.command` 可以继续进入正式版到开发版的既有单实例接管流程。启动器读取后立即删除这个一次性标记，且标记不纳入开发运行时身份摘要，避免向后续进程传播或让同一源码因不同合法入口被误判为后端变化。

## 定向验证

- 来源与身份契约 2/2 通过：内部工具环境仍拦截；精确外部标记解除误拦截；其他值不能解除；标记有无不改变运行时身份。
- macOS 隔离启动控制台与影响范围 3/3 通过：成功、失败两条入口均把外部标记传给启动脚本，仍保留增量日志和真实退出码；变更只影响 macOS 原生免费开发入口契约。
- `bash -n` 与 `git diff --check` 通过。

本轮未从当前 Codex 任务内执行真实接管，以免绕过本修复保留的会话保护。随后用户从外部重新打开修改后的 `.command`，实际开发注入器于 10:47 启动并加载 Widget 177，原 Codex app-server 进程仍保持 10:02 的 PID 与启动时间，证明这次接管没有重启 Codex。已安装正式应用的文件元数据仍为 0.1.293；它与当前运行的开发注入器分别记录。本轮后续页面修复已升至 Widget 178，仍需再次打开 `.command` 才会加载。
