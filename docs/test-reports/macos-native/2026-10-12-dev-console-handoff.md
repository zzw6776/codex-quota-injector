## 现场与修复

用户复现时一个 dev 0.1.311 后台运行，两个 `.command` Shell 及各自的两个 tail 仍存活。重复启动的日志明确显示“仅更新页面，保留 Router 与现有连接”。原脚本在启动调用返回后继续等待 `tail -F`，没有日志观察器交接。

新增观察器归属文件，使用原子替换和目录变更通知。最新观察器登记后，旧观察器仅通知自己的 Shell 正常退出；Shell 清理本窗口的日志 follower 和协调器，后台由 nohup 分离，继续运行。不轮询目录，不枚举或终止其他后台 PID。共享现有 macOS Node 环境准备，保留缺少依赖及准备失败的错误留窗。

新机制只适用于加载新版脚本的观察器；此前已运行的旧脚本没有归属监听，需用户关闭一次。没有为兼容旧日志窗口而杀后台或重启 Codex。

## 定向结果

- 首次 `console.tap`：3/4 通过，交接用例超时。诊断用例保留在 `handoff-debug.tap` 和 `handoff-diagnostic.tap`，没有把调试重跑累计为通过数量。
- 根因：macOS `/var` 与 `/private/var` 别名使 CLI 入口路径比较不一致，协调器未进入运行分支。改为 realpath 比较。
- 最终 `console-verified.tap`：5/5 通过，0 失败、0 跳过。覆盖影响范围分类、三个观察器并发归属、成功复用后的持续日志、启动失败完整输出、连续打开三次与后台 PID 不变、最新日志窗口正常关闭且后台继续存活。
- bash 语法及 diff 空白检查通过。使用真实 macOS Shell、Node、文件监听与日志进程，后台是隔离的无模型 fixture，不代替日常 GUI 启停验收。

## 模型目录 warn

警告由 OAuth 隔离探测未写出可用 `models_cache.json` 触发；官方 `debug models` 可能返回内置目录，因此仅命令成功不足以证明账号在线刷新。现实现保留上次目录并报告 warn，不能把这种回退改记为刷新成功。

本次执行已确认路径的官方 CLI `0.162.0-alpha.17.2`，隔离临时 CODEX_HOME、禁用 refresh token 和项目中继环境，目录探测取得 10 个模型并写出在线缓存，返回 source online，无 stderr 失败信号。临时目录按既有实现清理，没有写日常凭据或模型缓存。本地现存目录也有 10 个模型，账号存储与官方文件的访问凭据、ID 凭据及账号匹配；摘要不包含凭据或账号标识。

这证明当前目录接口可用，已有目录可继续使用；之前周期性失败的具体原因缺少充分证据，未归因为持续网络波动，也没有修改回退判据或日志级别。原日志另有旧正式版找不到新版 CLI 路径的记录，该不同错误不混入本次 warn 归因。
