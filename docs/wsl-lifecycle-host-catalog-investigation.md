# WSL 启停接管工具目录误报

2026-09-16 的启停恢复任务 `20260916150053-ae5663e4` 在正式 WSL 接管阶段仅 `hostToolsReady` 未就绪。Windows 原生启动、单实例、重连和关闭重开四项通过；原报告保留失败状态，不接受为上游通过。

实际官方桌面为 `26.908.40834`，Linux CLI 为 `0.154.0-alpha.6.2`。官方桌面在启动后为任务注册 codex_app MCP；其任务专属配置不一定出现在不传 threadId 的全局 `mcpServerStatus/list`。隔离副本中，官方直连与正式 Relay 都返回空全局列表；两者对 ready 通知对应的任务均返回 connected 和完整工具目录。对照未启动模型回合，未重启日常桌面。

项目健康检查收到 ready 通知后，只等待客户端再次读取目录，未主动核对该任务。旧的空全局目录仍被判为服务未注册，即使任务服务已就绪，也会造成启停恢复超时。Relay 82 在通知后增加仅一次在途的同任务目录核验，不执行 MCP 重载或模型请求；已核验的同任务就绪证据不被空全局列表推翻。明确失败、当前任务缺项或查询错误仍按失败记录，另一任务目录不能用于该规则。

同时，`src/platform/readiness.mjs` 的稳定 WSL 进程身份与旧版时间探针没有设置 windowsHide。后台轮询每次执行 wsl.exe 都可能创建可见控制台；已为两条路径设置隐藏窗口，仍保留 boot_id、启动 ticks 与旧版启动时间校验。启停回滚的源码启动入口也隐藏 Node 控制台。用户直接启动的开发版 cmd 持续显示日志的行为保留。

原监督器在回滚期间退出，Windows Task Scheduler 的 LastTaskResult 为 `3221225786`（`0xC000013A`，控制台中断）。用户随后明确说明是自行退出控制器，因此确认这部分由手动退出造成，不归因为 Relay 崩溃。原账号往返阶段尚未执行，不能宣称原账号已恢复。

修复发布版本 `0.1.280`，Relay 82，Widget 171。Windows 回滚以已验证的当前源码原生 Relay 恢复，单独记录 recoverySourceVersion 和 recoveryRelayProtocol，不把新版恢复成功当成原 0.1.279 完整验收通过。恢复监督器须等待当前活动回合终态和落盘后才关闭桌面。

证据位于 `.runtime/lifecycle-preparation-20260916/`：`host-status-comparison.json`、`host-status-fixed-source.json`、`host-status-fixed-native-elf.json`、`fix-wsl-tests.log`、`recovery-windows-tests.log`。Windows 定向测试 25/25、WSL 定向测试 25/25；Windows 生命周期与恢复契约测试 43/43。真实完整启停仍以正式任务报告为准。

后续策略调整：用户要求取消 Windows/WSL 验收回滚。现已移除旧安装备份、旧安装核对和回滚入口；旧报告仍保留真实失败，新验收直接安装当前候选版。上述旧版恢复问题不再作为新验收门禁。

macOS 同步移除旧应用备份与回滚；共享执行器失败时直接保存终态。历史报告仍可阅读，不再提供任何平台的 `--recover` 执行入口。

## 主页按需加载与无人点击验收（0.1.281）

用户指出 0.1.280 完整报告 `20260916153329-f2d92669` 的工具加载曾由手动进入任务促成。原始 18/18 报告保持不变，旁存 `manual-assistance.json`；该报告不能证明无需人工点击的启动验收。

进一步读取同一官方桌面的 `getCodexRequestConfig`、codex-app-tools 插件配置和深链接入口，确认当前桌面把工具配置绑定到任务；主页启动全局 app-server 不代表任务 MCP 已启动。Relay 82 的同任务目录核验解决了“已启动但未核验”，没有解决“主页尚未激活任务却开始计时”。这是项目健康状态与官方按需加载生命周期不一致。

0.1.281（Relay 83、Widget 172）日常保留主页，显示灰色“任务工具按需加载，进入任务后自动核验”。只有实际 codex_app 启动证据或实际服务条目进入启动流程，才执行超时检查。空全局目录不能掩盖明确失败、任务作用域下的服务缺失、禁用、工具缺项或查询错误；按需加载不表示工具已验证，也不能通过启停就绪门禁。

Windows/WSL 与 macOS 启停控制器在进程、目标协议及接管归属满足后，使用当前桌面可执行文件的官方 `codex://threads/<发起任务UUID>` 深链接自动打开发起任务。不创建测试任务、不发送模型回合；等待该任务的真实工具目录完整后才继续。多个检查点任务必须明确绑定发起任务，不能选择任意任务。每个桌面 PID 只尝试一次，报告记录激活方式、发起任务与回合、目标 PID 和验证时间。

Windows 可单独执行 `npm run test:lifecycle -- --plan --task-tools-only` 查看范围，或加 `--confirm-restart --task-tools-only --installer=<当前版本Setup路径>` 执行任务工具启动补测。该范围验证 Windows / WSL 启动与关闭重开、历史安全落盘、正式包、运行方式恢复及最终状态，不重复账号切换和模型冒烟；模型请求预算为 0。完整启停入口仍包含原有单实例、重连和账号往返。

本机已验证官方深链接保持现有桌面、注入器及 Relay PID 不变。Windows 和 WSL 各自使用原生依赖构建与执行；macOS 的启动命令及控制器等待契约在自动化测试覆盖，真实 macOS 桌面仍未在本机执行。定向日志和产物证据位于 `.runtime/lifecycle-preparation-20260916/lazy-task-tools-*`，真实启停补测以独立报告为准。
